# Data and Cache Isolation

Choose one state model per worktree and make it explicit in `COMPOSE_FILE`.

## Model A: shared servers, isolated namespaces

Use `compose.shared-data.yaml` when a central PostgreSQL/Redis stack is already running. The app joins an external data network, but every worktree gets distinct logical state.

### PostgreSQL

Minimum isolation is one database per `STACK_ID`; stronger isolation uses one role per worktree as well. Provision from an administrative connection, not from the app container:

```sql
CREATE ROLE app_feature_a1b2c3 LOGIN PASSWORD '<generated-secret>';
CREATE DATABASE app_feature_a1b2c3 OWNER app_feature_a1b2c3;
REVOKE CONNECT ON DATABASE app_feature_a1b2c3 FROM PUBLIC;
GRANT CONNECT ON DATABASE app_feature_a1b2c3 TO app_feature_a1b2c3;
```

Use identifier-safe values generated by the helper; do not splice an untrusted branch name into SQL. Store the generated password only in the gitignored worktree `.env` or a secret manager.

Distinct databases prevent branches with incompatible migrations from corrupting each other. Distinct schemas can work, but connection defaults, migration history tables, extensions, and search paths are easier to get wrong. Prefer databases unless server policy forbids them.

The shared server must have a reliable backup policy. Development isolation is not a substitute for backup, although both are frequently discovered during the same regrettable afternoon.

### Redis/Valkey

Give every worktree a required `REDIS_PREFIX` and ensure the application applies it to every key, lock, channel, cache tag, rate-limit bucket, and background-job key. Redis logical database numbers do not isolate ACLs, memory eviction, pub/sub, or operational mistakes. For strong isolation, create ACL users with key patterns or use separate instances.

### Other shared systems

- RabbitMQ: unique virtual host per worktree.
- Kafka: prefix topics, transactional IDs, and consumer groups.
- S3-compatible storage: unique bucket or enforced object prefix.
- Elasticsearch/OpenSearch: unique index prefix and aliases.
- ClickHouse: unique database.
- OAuth providers: unique redirect URIs/clients when callbacks differ by hostname.

## Model B: one data stack per worktree

Use `compose.worktree-data.yaml` plus `COMPOSE_PROFILES=worktree-data`. PostgreSQL and Redis remain on the private project network and use project-scoped volumes. This costs more RAM and disk but provides the cleanest migration and destructive-test isolation.

The profile is selected in `.env`, so bare commands remain uniform:

```text
COMPOSE_FILE=compose.yaml:compose.dev.yaml:compose.worktree-data.yaml:compose.tls-internal.yaml
COMPOSE_PROFILES=worktree-data
```

On Windows, use semicolons in `COMPOSE_FILE`.

Never set explicit volume `name:` values in the worktree data overlay. Compose's project prefix is the isolation mechanism. `docker compose down` preserves volumes; `docker compose down --volumes` destroys them and must be an explicit, reviewed cleanup action.

PostgreSQL 18+ official images use a major-version-specific `PGDATA` below `/var/lib/postgresql` and reject the old `/var/lib/postgresql/data` mount layout. For `postgres:18-*`, mount the project-scoped volume at `/var/lib/postgresql`; use the image's declared volume/`PGDATA` contract when selecting another major version. Do not casually change this target on an existing volume—database-major upgrades require a real upgrade or dump/restore, not optimistic remounting.

## Readiness and migrations

Containers starting in order does not prove the database accepts connections. Add a healthcheck and make the app retry transient startup failures. If multiple application replicas can migrate, use a database advisory lock or a dedicated migration job. Different worktrees must never point at the same migration-history table.

For automated tests, continue using disposable Testcontainers rather than a developer's shared database. The Compose data mode exists for running the application, not for making integration tests depend on whoever last edited a workstation database.

## Selection guide

| Need | Choose |
|---|---|
| Lowest resource usage, compatible schemas | Shared servers + unique DB/prefix |
| Branches change migrations heavily | Per-worktree data |
| Destructive/manual data experiments | Per-worktree data |
| Large immutable reference dataset | Shared read-only source + worktree-local writes |
| CI integration tests | Testcontainers, independent of either dev mode |

## Cleanup

List the rendered project and volumes before removal. Stop the worktree stack first. Delete its volumes only after confirming `com.docker.compose.project` equals that worktree's `COMPOSE_PROJECT_NAME`; fixed names and stale shell variables can otherwise turn cleanup into cross-project vandalism with excellent command-line ergonomics.
